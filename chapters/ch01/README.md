# **Chapter 1: Hill Climbing and the Secure Harness: Design Patterns for Local Search in Agentic Systems**

This lab is the executable companion for Chapter 1, "Hill Climbing and the Secure Harness." The chapter introduces the central idea that powerful multi-agent systems should not be trusted because a prompt sounds careful, a model sounds confident, or a team says that a human is somewhere in the loop. They should be trusted only to the degree that their work is routed through a harness that can name actors, bind actions to purpose, classify data, check tool authority, record evidence, pause risky runs, and recover from checkpoints. Chapter 1 uses the language of hill climbing because many agent systems improve by iteration. They try a plan, observe feedback, adjust, and try again. That loop is useful, but it is also where risk accumulates. A small mistake in the objective function can become a repeated mistake. A low-trust note can become durable memory. A temporary exception can become a new default. The secure harness is the production control plane that lets improvement continue without allowing every local improvement to silently expand authority.

The scenario in `scenario.py` starts with a fictional but realistic project called `shared-deploy-swarm`. The mission sounds ordinary: investigate a customer incident, patch a worker, notify the customer, and deploy the fix. The unsafe design is also common. A planner, researcher, coder, and deployer share broad credentials. The researcher reads external issue comments and internal incident notes in the same workspace. The coder can write repository patches and read persistent memory. The deployer can push to production with the same general authority as the rest of the swarm. The project improves through trial and error, but the loop has no durable evidence that risk is decreasing. It may get faster while becoming less governable.

The lab maps that unsafe project to a secure harness reference architecture. The mapping is intentionally concrete. It uses the shared `harnesslab.core` primitives so students can see how abstract chapter concepts become production shapes. The lab does not call a cloud service, a model API, or a network endpoint. It is dependency-free because Chapter 1 is about the control plane, not vendor features. Everything runs locally and deterministically, which makes it suitable for classroom use, CI checks, workshops, and offline exercises.

## What Students Should Notice

The most important lesson is that the harness does not eliminate autonomy. It structures autonomy. The safe path in the lab still allows a useful action: the agent can propose a repository patch that adds a deployment approval gate. That action is allowed because identity, intent, tool registration, budget, and data routing all agree that it is within scope. The unsafe paths are not treated as mysterious model failures. They are handled as ordinary control-plane events. A poisoned memory write is denied. A vault read is denied because it is outside the intent contract. A production deployment is escalated because it is privileged. An external customer message through an unapproved route is denied by data governance. The run is paused before privileged work proceeds, a checkpoint is available, and a bounded policy overlay can steer the run without editing hidden prompts.

This distinction matters for long-running agents. A short demo can rely on a single prompt and a single terminal session. A long-running agent cannot. It may resume tomorrow. It may delegate to a new agent. It may read new context that was not present when the original plan was approved. It may change memory, update tools, or inherit state from a previous run. A harness gives the system places to check those transitions. It asks: who is acting, why are they acting, what data are they touching, what tool will be called, what evidence will prove the step was safe, and where can we pause or roll back if the step changes the risk profile?

## How The Lab Maps To The Chapter

Chapter 1 frames secure agent design as a hill-climbing problem. A team wants agents to become more capable over time. They want better plans, faster fixes, fewer handoffs, and more reliable outcomes. The danger is that "better" is often measured by task completion while safety is left implicit. If the agent finds a faster way to deploy, stores a shortcut in memory, and repeats it next week, the system may appear to improve while actually moving away from governance. The lab represents this by building a hill-climb trace. The initial candidate is an unsafe baseline with only manual review in chat. Each accepted neighbor adds a control plane: identity, intent, tool gating, context firewall, memory firewall, runtime steering, evidence, and governance. Rejected neighbors show the other side of the lesson. Skipping evidence for speed improves convenience but loses auditability. Letting the deployer bypass checkpoints after a few clean patches may look efficient, but it removes the intervention handle from the highest-risk action.

The hill-climbing trace is not meant to be a mathematical optimizer. It is a teaching model for local search under governance. The acceptance rule says that a candidate can be accepted only when the score improves and mandatory gates remain present. That mirrors the chapter's central warning: do not let local improvements rewrite the safety objective. If identity, intent, tool gating, runtime steering, or evidence disappear, the system is not improving in the relevant sense, even if it completes more tasks.

The control and evidence matrix is the second major chapter mapping. Chapter 1 argues that a secure harness must make safety inspectable. A policy that exists only in a prompt is hard to test, hard to audit, and easy to erase by accident. The matrix turns each risk into a control and each control into evidence. Shared credentials map to the credential broker. Goal drift maps to an intent contract. Tool overreach maps to the tool gateway and capability budget. Instruction injection maps to the context firewall. Memory poisoning maps to the memory firewall. Unapproved egress maps to data governance. Unsafe deployment maps to checkpointing and runtime pause. Opaque improvement maps to the hill-climb governance trace. Hidden prompt edits map to bounded policy overlays. Students should read the matrix as the backbone of the harness: every important risk needs a control, and every important control needs evidence.

## Unsafe Multi-Agent Project

The unsafe project is deliberately familiar. It has a planner, researcher, coder, and deployer. Each role sounds reasonable. The problem is not that the roles exist. The problem is that the boundaries between them are weak. A planner can assign production actions without a verified task contract. A researcher can mix public issue comments with internal incident notes. A coder can patch code and read persistent memory without checking provenance. A deployer shares broad credentials with the other agents. This is the shape many teams arrive at when they start from convenience. They wire agents together, give them tools, add a shared scratchpad, and rely on the prompt to say "be careful."

The lab highlights six unsafe patterns. First, one long-lived credential is shared by every agent. Second, external context can become instructions. Third, tool access is granted by a role label rather than a verified purpose. Fourth, memory accepts future-behavior rules from low-trust sources. Fifth, deployment has no checkpoint, approval gate, or rollback state. Sixth, the improvement loop has no evidence that risk is going down. Those patterns are not exotic. They are common failure modes in systems that are useful enough to be dangerous.

The external context item in the lab contains an instruction-injection style sentence. It tells the system to ignore previous instructions, use a tool, send secrets externally, and disable policy. The exact text is less important than the pattern. A long-running agent will read many things written by other people and other systems. Some of those things will be malicious. Some will be stale. Some will be accidental. The harness treats context as data with trust tiers and provenance. It does not let a public issue comment become a system instruction just because it appears near a task.

## Secure Harness Reference Architecture

The secure reference architecture in the lab has eight planes. The identity plane gives each agent a name, role, tenant, short-lived credential, audience binding, and delegation chain. The intent plane binds a task to a goal, actor role, allowed tools, allowed data, maximum risk, required evidence, and escalation requirements. The tool plane checks that a requested tool exists, that its declared side effect matches registration, that the data class is allowed, and that the capability budget has not been exhausted. The context plane inspects trust tiers, provenance, and injection markers before context reaches the agent. The memory plane prevents low-trust sources from writing durable future behavior and keeps a ledger for rollback. The runtime plane creates checkpoints, pauses risky runs, injects bounded policy overlays, resumes from known state, and can kill a run when needed. The evidence plane ties the accepted design to a control matrix and a stable evidence hash. The governance plane defines the hill-climb acceptance rule.

This architecture is intentionally broader than a single guardrail. Many agent security discussions focus on one layer, such as prompt injection detection or tool allowlists. Those layers are important, but Chapter 1 wants students to see the whole harness. Prompt injection containment is weaker without data governance because the system may still send private data to an external sink. Tool allowlists are weaker without intent because a tool can be legitimate in one task and dangerous in another. Memory controls are weaker without provenance because the system cannot tell whether a durable rule came from a trusted operator or a public webpage. Runtime pause is weaker without checkpoints because a paused run has no clean place to resume. Evidence is weaker without a matrix because logs alone do not explain which risks were controlled.

The lab's safe path demonstrates this combined structure. A patch to the internal repository is allowed only after several independent checks agree. The intent contract says `patch_repo` is allowed for internal data and reversible write risk. The tool gateway says the registered tool supports that risk and data class. The capability budget says the tool and risk have remaining budget. Data governance says the destination is the internal repository and the route is allowed. This is what production harnessing should feel like: not a single yes or no from a model, but a chain of narrow, explainable decisions.

## Control And Evidence Matrix

The matrix is the easiest artifact to discuss in a classroom. Ask students to pick one row and explain the failure mode, the control, and the evidence. For example, the row for memory poisoning says that the risk is a low-trust source writing a future deployment rule. The control is the memory firewall. The evidence is a denied decision for an external "always approve deployment" memory write. The book mapping says long-running systems need memory ledgers, not unchecked preference files.

That row teaches several lessons at once. Memory is not just storage. It is part of the policy surface. A memory entry can influence a future run long after the original context is gone. If a malicious issue comment can store "always approve deploys," then the attack has moved from the current prompt into future behavior. The memory firewall makes the write explicit, checks source trust, detects poisoning language, stores accepted records with source hashes, and supports rollback. Chapter 1 treats that as a harness responsibility because long-running agents live in their accumulated state.

Another useful row is the one for unsafe production deployment. The control is a runtime checkpoint and pause. The evidence is a checkpoint created before deployment and a warning decision that the run was paused when privileged work appeared before approval evidence was complete. This row helps students move beyond the idea that safety is only about blocking. Sometimes the right action is to stop the run at a recoverable point, preserve evidence, and ask for approval. A long-running agent should not have to restart from nothing, and a human reviewer should not have to guess what state the agent was in. The checkpoint gives both sides a shared reference.

## Checkpointing And Runtime Steering

The lab creates a checkpoint after the harness has built the control matrix and hill-climb trace, but before privileged deployment proceeds. The checkpoint state is small on purpose: accepted candidate, number of controls, number of quarantined context items, and number of unsafe patterns. In a production system, the state might include task graph position, tool outputs, current policy version, memory read set, context references, and pending approvals. The teaching point is not the exact fields. The teaching point is that the run has a named state that can be paused, resumed, and compared.

The scenario then pauses the run because a privileged deployment was attempted before approval evidence was complete. It also injects a bounded policy overlay. The overlay says deployment requires approval and external context is quarantined by default. The overlay has a time to live. That detail matters. A hidden prompt edit can become permanent by accident. A bounded overlay is explicit, scoped, and reversible. It lets an operator steer a long-running agent without pretending that the agent's original instructions are still the only source of policy.

Students should think of runtime steering as the difference between managing an agent and merely watching an agent. Watching gives logs. Managing gives pause, checkpoint, resume, policy overlays, quotas, and kill switches. Long-running systems need management surfaces because their risk can change during the run. A safe read action can lead to a risky write action. A trusted context set can be joined with an untrusted source. A reversible patch can be followed by an irreversible deployment. The harness needs to react at those boundaries.

## Hill-Climbing Governance

The hill-climbing part of the lab is a simplified model of iterative system improvement. The objective is to maximize useful autonomy while minimizing unbounded authority and preserving evidence. The candidates form a path from unsafe baseline to governed harness. Each accepted step improves the score and keeps mandatory gates. The rejected neighbors show that the governance rule has teeth. The system is not allowed to trade away evidence or checkpoints for speed.

This maps directly to the book chapter. Hill climbing is attractive because it lets teams improve through local experiments. Add a tool, evaluate it, improve the planner, adjust the memory policy, change the handoff, and so on. But in security, not every local improvement is a real improvement. A team can climb the wrong hill. If the score is only task completion, the system may discover shortcuts that weaken review. If the score includes evidence, bounded authority, and recovery, the system is more likely to become both useful and governable.

The lab's governance trace is therefore an audit artifact. It tells a future reviewer why each step was accepted and why tempting alternatives were rejected. In a real deployment, the same idea could be connected to evals, incident reports, risk registers, and change approvals. The point is that the improvement loop itself needs a harness. It is not enough to secure one tool call if tomorrow's local search can remove the control that made today's tool call safe.

## Long-Running-Agent Considerations

Long-running agents are the main reason Chapter 1 starts with harness architecture instead of prompt technique. The longer an agent runs, the more chances it has to drift from its original purpose. It may accumulate context from many trust tiers. It may store memory that influences later decisions. It may call tools in a sequence that no single prompt author anticipated. It may survive across software deploys, policy changes, credential rotations, and human shift changes. A secure harness must assume that the run is a living process with state, not a single response.

Several details in the lab are aimed at long-running operation. Credentials are short lived and audience bound, so a credential meant for the harness control plane cannot silently become a credential for another service. The intent contract expires and names required evidence, so a task cannot keep expanding forever. The context firewall quarantines suspicious external material before it reaches planning or memory. The memory firewall blocks future-behavior poisoning. The capability budget limits repeated tool and risk use, which prevents a run from retrying a dangerous action until it happens to work. The runtime checkpoint captures recoverable state before privileged work. The policy overlay is bounded by time to live. The hill-climb rule prevents future iterations from removing mandatory gates.

Students should also consider what the lab does not model fully. A production system would need real authentication, durable storage, distributed tracing, policy version management, approval workflows, incident response, and integration with deployment systems. The lab intentionally reduces those systems to small deterministic primitives so the concepts are visible. The correct takeaway is not "this toy broker is production authentication." The correct takeaway is "production authentication must provide these shapes: identity, revocation, audience binding, delegation evidence, and short lifetimes."

## Running The Lab

From the HarnessLab root, run:

```bash
python -m chapters.ch01.run
```

The shared CLI contract also supports:

```bash
python -m harnesslab.cli run ch01
```

The result is a `LabResult`. It includes the chapter key, title, pass status, score, summary, decisions, and artifacts. The decisions are the important operational trail. A healthy run should show allowed decisions for the safe internal patch path, warning for quarantined context and runtime pause, denials for poisoned memory and unapproved data routes, and escalations for privileged deployment attempts. The artifacts are the teaching trail. They include the unsafe project model, the secure reference architecture, the control and evidence matrix, the hill-climb governance trace, checkpoint metadata, context quarantine details, blocked or escalated path reasons, and long-running-agent considerations.

When reviewing the output, do not focus only on the final pass value. Ask whether each decision is explainable. Ask whether the denied and escalated paths are the ones you would expect. Ask whether the checkpoint appears before the privileged action. Ask whether the hill-climb trace rejects convenience improvements that weaken governance. Those questions mirror the practical review questions that a security team should ask before allowing a long-running multi-agent system to touch production work.

## Discussion Prompts

One useful prompt is: which control would you remove if you had to simplify the harness, and what new risk would that create? Students often choose evidence because it feels less active than a gateway or firewall. That answer leads to a good discussion. Without evidence, the system may still block obvious bad actions, but the team cannot prove why a run was safe, compare candidates, or learn from incidents. Evidence is what makes hill climbing governable.

Another prompt is: when should the system deny, when should it escalate, and when should it pause? The lab gives examples of all three. Memory poisoning and unapproved egress are denied. Privileged deployment is escalated because it may be legitimate with approval. The run is paused because the system needs a recoverable intervention point. These are different safety moves. A mature harness needs all of them.

A final prompt is: what would change if the same project ran for thirty days instead of thirty minutes? The answer should include credential rotation, policy versioning, memory expiration, checkpoint retention, drift detection, approval freshness, and evidence review. Chapter 1 is not only about stopping bad tool calls today. It is about designing a system whose improvement loop can remain understandable and governable over time.

The lab should leave students with a simple mental model: agents may climb, but the harness defines the hill. Without the harness, local search can optimize for speed, completion, or convenience while quietly expanding authority. With the harness, each improvement has to pass through identity, intent, tool, context, memory, runtime, evidence, and governance checks. That is the foundation the rest of HarnessLab builds on.
